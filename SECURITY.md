# Security Policy

## Supported versions

Until the project begins publishing supported releases, security fixes are made against the current `main` branch. Release-specific support windows will be documented when executable releases are introduced.

## Reporting a vulnerability

Do not report suspected vulnerabilities in a public issue, discussion, pull request, or commit message.

Use GitHub's private vulnerability reporting or a private repository security advisory for this repository. Include:

- affected component and version or commit;
- impact and realistic attack scenario;
- reproduction steps or proof of concept;
- relevant configuration and environment details;
- suggested remediation, when known;
- whether the report may be shared with downstream maintainers.

If GitHub private reporting is unavailable, contact the repository owner through the private contact method published on the maintainer's GitHub profile. Do not disclose details publicly while a report is being evaluated.

## Response process

Maintainers will acknowledge receipt, assess severity and scope, preserve evidence, coordinate remediation, and determine disclosure timing. Acknowledgment does not imply confirmation. Reporters may be asked for additional evidence or validation.

Security decisions, risk acceptance, release approval, and disclosure timing remain human-authorized actions.

## Scope

Security reports may cover source code, automation, dependencies, schemas, agent prompts and contracts, orchestration, evidence handling, authorization boundaries, deployment material, and documentation defects that could lead to insecure implementation.
